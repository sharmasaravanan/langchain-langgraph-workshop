Module 1

The Agentic AI Ecosystem

Before we can architect anything, we need a shared vocabulary. This module builds the mental model everything else in the workshop stands on.

1.1 Evolution: from LLMs to agents

Start with what a large language model actually is: a function that takes text in and predicts text out. Extraordinarily good at that one job — but it has no hands, no memory between calls, and no opinion about what happens after it answers. Every time you call it, it's meeting you for the first time.

An agent is what you get when you wrap that same model in a loop: give it a goal, let it look at the world (read a file, check an API, see a tool's result), decide what to do next, act, and check again — repeatedly, without a human clicking "continue" at every step.

Nothing about the model changed. What changed is the scaffolding around it: memory, tools, and a loop that keeps calling the model with fresh context until the job is actually done.

The short version
Plain completion → turn-based assistants → tool-calling → multi-step agents → standing agent infrastructure. Each stage keeps the same model underneath and adds one more piece of scaffolding around it.
🤔 Think about it
Where's the task at your job right now that's basically "plain completion in a trench coat" — someone still has to babysit every single step?

1.2 AI agents vs. agentic workflows

These two terms get used interchangeably, and that's where most confusion starts.

An agentic workflow is a sequence of steps a person designed in advance — the order is fixed; only the content generated inside each step comes from a model. Think of a résumé screener: extract fields, score against criteria, draft a summary. The path never changes, only what fills it does.

An agent is a system where the model itself decides the path — which step to take next, which tool to call, when it's actually done. You hand it a goal, not a flowchart.

Agentic workflowAI agent
Who decides the next stepThe developer, in advance (a fixed graph)The model, at runtime
PredictabilityHigh — same input, same pathLower — path can vary run to run
Best forRepeatable, auditable processesOpen-ended, ambiguous goals
Main riskBrittle when reality doesn't match the flowchartCost, latency, and getting stuck in loops

Most real systems in production right now sit somewhere in between — an agentic workflow with one or two nodes where the model gets real discretion. We'll come back to this spectrum in Module 2.

1.3 Agent components: models, tools, memory, state & planning

Every agent, regardless of framework, is built from the same five ingredients. Learn to spot them, and any agent — however fancy the marketing — stops looking mysterious.

Model
The reasoning core. Given the current context, it decides what to say or do next. The only piece that's actually "thinking."
Tools
The hands. Functions or APIs the agent is allowed to call: search the web, run code, query a database, send a message. Without tools, an agent can only talk.
Memory
What persists across time. Short-term memory is this task's scratchpad; long-term memory is facts and past interactions the agent can recall in a future, unrelated run.
State
The live working data of this particular run: which step you're on, what's been tried, what's still pending. Unlike memory, state usually doesn't survive past this one execution.
Planning
How the agent decides ordering. Sometimes it plans the whole sequence upfront; more often, in real agents, it re-plans after every observation — decide one step, see what happened, decide the next.

1.4 Agent lifecycle

Put those five ingredients in motion and you get a loop. This is the loop, and almost every agent you'll ever debug is some variation of it.

  • Perceive — take in the current task, conversation, and any new tool results.
  • Plan — decide the single next action: call a tool, ask a clarifying question, or finish.
  • Act — actually do it: execute the tool, send the message.
  • Observe — read what came back: success, error, new data.
Where it breaks in production
A bad "Observe" step — one that silently swallows an error — sends garbage into the next "Plan" step, and the agent confidently does something wrong. Debugging agents is mostly about instrumenting this loop, not the model.

1.5 The current agentic AI ecosystem

A fast map of where the money, the users, and the arguments are right now, layer by layer.

  • Model providers — Anthropic (Claude), OpenAI, Google (Gemini), plus a growing set of open-weight models teams self-host for cost or data-residency reasons.
  • Agent frameworks & SDKs — graph-based orchestration (LangGraph is close to a default here), role-based multi-agent frameworks (CrewAI), and lighter SDK-native options each major lab now ships directly (OpenAI's Agents SDK, Google's ADK, Anthropic's Claude Agent SDK).
  • Interop protocols — MCP (Model Context Protocol) standardizes how an agent connects to tools and data; A2A (Agent-to-Agent) standardizes how two independent agents talk to each other. This layer will likely matter more than any single framework choice.
  • Supporting infrastructure — vector databases for long-term memory, checkpointing for durability, and observability tooling, because "why did my agent do that" is the most common sentence on any team running agents in production.

Frameworks will keep churning — one popular multi-agent framework already moved to maintenance mode this year while its own maker folded those ideas into a newer, unified framework. What's more durable: the five components and the loop you just learned. Learn those, and picking up (or dropping) any given framework becomes a week of ramp-up, not a philosophy change.

Module 2

Agent Framework Architecture

Module 1 gave you the vocabulary. Module 2 opens the hood: what a framework is actually doing for you, and where the real design decisions live.

2.1 Why agent frameworks?

You could build an agent with nothing but raw API calls, and plenty of people did, in 2023. It looked like: parse the model's tool-call output by hand, manage retries when a tool times out, keep the conversation history from silently growing past the model's context window, and write your own logging so you can find out why it did something insane at 2 a.m.

None of that is where your judgment adds value. A framework exists for the same reason a web framework exists: so you spend your time on what should this system decide and do, not how do I not lose my message history.

The trade-off is real: frameworks add abstraction, and abstraction can hide exactly the behavior you need to debug. Knowing the five components and the loop from Module 1 is what lets you look past any framework's syntax straight at what it's actually doing.

2.2 Framework architecture

Strip the branding off any agent framework and you'll find close to the same stack, top to bottom:

  • Your application — the actual task you're solving.
  • Orchestration — the loop or graph that decides what runs next. This is where "agentic vs. deterministic" lives.
  • Tools — schemas, plus the real functions they call.
  • Memory & state — what's remembered across runs, and what's tracked within one.
  • Prompts & context — how everything above gets assembled into what the model actually sees.
  • Model interface — a thin, swappable layer so the same agent can run on Claude, GPT, Gemini, or a local model.

When a framework feels confusing, it's almost always because two of these layers got tangled together in the docs. Untangle them and it usually clicks.

2.3 Models & prompts

Three things do the heavy lifting here.

System prompts set the agent's standing instructions — role, constraints, tone — separate from whatever the user or a tool just said.

Prompt templates turn static instructions plus live variables (today's date, the user's name, a retrieved document) into the actual message sent to the model, so you're not hand-writing prompts for every run.

Structured output is what makes agents reliable rather than charming: instead of free-form prose, you ask the model to answer inside a fixed schema — specific fields, specific types — so your code can parse it without guessing.

2.4 Tools & function calling

This is the mechanism that turns "a model that talks" into "a model that does." Three moving parts: you describe a tool, the model asks for it by name when it needs that capability, and your code runs the real function and hands the result back.

The part people underrate
The description you write for a tool does more work than the code behind it. A vague description gets called at the wrong moment, with the wrong arguments — write it like documentation for a very literal new teammate.

2.5 State & memory

State is the working data threaded through one execution — usually a plain object that gets passed from step to step and grows as the run progresses: which step you're on, what's been tried, partial results.

Memory outlives the run. Short-term memory is usually the running conversation, trimmed or summarized once it gets too long for the model's context window. Long-term memory is what lets an agent recall something from a completely different session — typically by embedding text into vectors and searching for what's relevant, or by keeping an explicit profile that gets loaded in at the start.

The distinction that trips people up: state is per-run and disposable; memory is cross-run and durable. Conflating them is a common source of agents that either forget everything or never let go of stale context.

def add_to_memory(history, new_message, max_messages=20):
    history.append(new_message)
    if len(history) > max_messages:
        # keep the system prompt, summarize the rest
        history = [history[0], {"role": "system",
                    "content": "...earlier conversation summarized..."}] + history[-5:]
    return history

2.6 Agent loops

The most common loop pattern has a name: ReAct — reason, then act, then observe, repeat. In plain terms: the model thinks about what to do, does one thing, looks at what happened, and thinks again with that new information — instead of trying to plan the entire task in one shot.

def agent_loop(task, model, tools, max_steps=6):
    history = [{"role": "user", "content": task}]
    for _ in range(max_steps):
        thought = model(history)                    # Reason
        if thought["done"]:
            return thought["answer"]
        tool_fn = tools[thought["tool_name"]]        # Act
        result = tool_fn(**thought["tool_args"])
        history.append({"role": "tool", "content": result})  # Observe
    return "Stopped: hit max_steps safeguard."
Three things every production loop needs (that no tutorial mentions)
A max-steps limit, so a confused agent doesn't run forever. A cost or time budget. And an explicit "stop" signal the model can raise itself, rather than your code guessing when it's done.

2.7 Workflow orchestration

Once you have more than one step, you need to decide the shape of the flow, not just the loop:

Linear — simplest, most predictable, least flexible.

A→B→C

Branching — a check early on sends execution down one of several fixed paths.

Classify→Path APath BPath C

Parallel fan-out / fan-in — independent sub-tasks run at once, then results merge.

Split→Task ATask BTask C→Merge

Supervisor–worker — one "manager" agent delegates to specialists, then combines what comes back.

Supervisor→Worker 1Worker 2Worker 3→Combined result

Frameworks like LangGraph make this explicit — you're quite literally drawing the graph of nodes and edges. Simpler frameworks hide it as a plain list of steps. The shape doesn't disappear just because you can't see it in the code.

2.8 Deterministic vs. agentic workflows

Zoom out and everything in this workshop sits on one spectrum.

At one end: a fully deterministic pipeline. The steps are fixed by a developer; the model only fills in content inside each step. Predictable cost, predictable latency, easy to audit — and brittle the moment reality doesn't match what you designed for.

At the other end: a fully agentic system. The model decides which tools to call, in what order, and when to stop. Flexible enough to handle situations you didn't anticipate — and harder to predict, price, or fully audit.

Almost nothing production-grade lives at either extreme. Most real systems are hybrid agentic workflows: mostly fixed steps, with one or two places where the model genuinely gets to decide.

Lean deterministic when...Lean agentic when...
The task is repeatable and well-understoodThe task is novel each time
You need auditability or predictable costYou need judgment across paths you can't enumerate
e.g. invoice processing, compliance checkse.g. research assistants, debugging help
Quick check: your company's expense-approval bot always runs verify-receipt → check-policy → approve-or-flag, no exceptions. Deterministic, agentic workflow, or full agent?
Deterministic pipeline — dressed up as an "AI agent" in the marketing deck. Nothing about the control flow is actually up to the model.
