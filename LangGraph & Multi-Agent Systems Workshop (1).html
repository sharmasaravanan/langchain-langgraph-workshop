1. LangGraph Fundamentals

~45 min

Ever built an LLM app that worked great in the demo, then fell apart the moment it needed to retry, backtrack, or wait for a human? That's the gap LangGraph fills — think of it as trading a straight highway for a subway map, with junctions, loops, and stations where the train can pause.

Why LangGraph?

Plain prompt chains run once, start to finish. Real workflows need to branch, retry, and remember — that needs a graph, not a script.

Graph-Based Workflows

Model your app as a flowchart: circles do the work, arrows decide what happens next.

State

One shared object that travels through every step — like a case file that gets updated as it's passed between departments.

Nodes

Just Python functions: read the state, do something (call a tool, call an LLM), return an update.

Edges

The wiring between nodes. A plain edge always goes A → B, no questions asked.

Conditional Routing

An edge that asks a question first: "Did we get a good answer? If not, go back and search again."

Loops

Send state back to an earlier node to retry or refine — with a limit, so it doesn't spin forever.

Checkpoints & Persistence

Save state at every step, so a crash — or a human review — can resume exactly where it left off.

Code Example

from langgraph.graph import StateGraph, END
from typing import TypedDict

class State(TypedDict):
    question: str
    answer: str
    attempts: int

def search(state: State) -> State:
    state["attempts"] += 1
    state["answer"] = call_llm(state["question"])  # your LLM call here
    return state

def is_good_enough(state: State) -> str:
    if "I don't know" in state["answer"] and state["attempts"] < 3:
        return "retry"
    return "done"

graph = StateGraph(State)
graph.add_node("search", search)
graph.set_entry_point("search")
graph.add_conditional_edges("search", is_good_enough, {"retry": "search", "done": END})

app = graph.compile()
result = app.invoke({"question": "Explain LangGraph", "attempts": 0})
print(result["answer"], "in", result["attempts"], "attempt(s)")

🎯 Hands-on: Build a "Draft & Critique" Graph (20 min)

  • Node A drafts a short answer to a question of your choice.
  • Node B critiques the draft — too short? missing detail?
  • Conditional edge: if the critique says "needs work" and attempts < 3, loop back to Node A. Otherwise, END.
  • Print the final state — how many attempts did it actually take?

2. Multi-Agent Systems

~45 min

One agent juggling ten tools and a 500-line prompt starts to behave like an overworked generalist doctor trying to also be the radiologist, pharmacist, and surgeon. Sometimes the fix isn't a smarter agent — it's a smaller, better team.

Single vs Multi-Agent

One agent is simpler to reason about — until its job gets too big to fit in one prompt or toolset.

Specialist Agents

Give each agent one job — researcher, coder, reviewer — like a hospital's specialists instead of one doctor for everything.

Supervisor Pattern

A "manager" agent looks at the task and decides which specialist handles it next.

Sequential & Parallel Agents

Sequential: a pipeline, one after another. Parallel: several agents work at once, results get merged.

Agent Communication

Agents pass messages or structured data to each other — a Slack thread, not telepathy.

Shared State

All agents read and write the same state object, so nothing gets lost between handoffs.

When to Use Multi-Agent

Reach for it when tasks are genuinely separable, or one agent's instructions have become unmaintainable — not by default.

Code Example — Supervisor Pattern

def supervisor(state):
    if "research" not in state:
        return {"next": "researcher"}
    if "draft" not in state:
        return {"next": "writer"}
    return {"next": "end"}

graph.add_node("supervisor", supervisor)
graph.add_node("researcher", researcher_agent)
graph.add_node("writer", writer_agent)

graph.add_conditional_edges("supervisor", lambda s: s["next"], {
    "researcher": "researcher", "writer": "writer", "end": END
})
graph.add_edge("researcher", "supervisor")
graph.add_edge("writer", "supervisor")

  • Name the one piece of shared state every agent in your team needs to see.

3. Agent Limitations, Governance & Responsible AI

~45 min

Autonomy is the whole point of agents — and also exactly why they're riskier than a chatbot that only talks. An agent that can act can also act wrong. This module is about noticing that before your users do.

Hallucinations

Confident wrong answers — and in a multi-step agent, one wrong "fact" can get treated as truth by the next step.

Tool Misuse

Wrong parameters, wrong tool, or the right tool at the wrong moment — e.g. calling delete instead of get.

Non-Deterministic Behaviour

Same input, different output, run to run — makes testing harder than traditional software.

Context Limitations

Long conversations or large tool outputs can push earlier reasoning out of the model's working memory.

Prompt Injection

Instructions hidden in a webpage, PDF, or email the agent reads — and obeys — as if you'd typed them yourself.

Data & Privacy Risks

Broad tool access can pull sensitive data into a response, a log, or the wrong system entirely.

Access Control

Give each agent the minimum tools and permissions it needs — never admin access "just in case".

Human Oversight

Add approval checkpoints before high-stakes actions — sending an email, moving money, deleting data.

Evaluation & Monitoring

Log every step, trace decisions, run automated evals — so failures surface before customers find them.

Code Example — Human-in-the-Loop Approval

graph = StateGraph(State)
graph.add_node("draft_email", draft_email)
graph.add_node("send_email", send_email)  # a sensitive, irreversible tool
graph.add_edge("draft_email", "send_email")

app = graph.compile(
    checkpointer=memory_saver,
    interrupt_before=["send_email"]  # pause here for a human to review
)

result = app.invoke(initial_state, config)
# ... a human reads result["draft"] and approves ...
app.invoke(None, config)  # resume only after sign-off

4. Framework Comparison & Architecture Decisions

~45 min

New agent framework, every month. The real skill isn't knowing all of them — it's knowing which one (if any) your problem actually needs.

ApproachBest ForControl LevelLearning Curve
LangGraphComplex, stateful, custom control flowHighMedium–High
CrewAIFast prototyping, role-based agent teamsMediumLow
AutoGenConversation-driven agent collaborationMediumMedium
No FrameworkSimple, deterministic, single-call tasksFull (it's just code)—

LangChain vs LangGraph

LangChain gives you building blocks — prompts, tools, chains. LangGraph gives you the engine to orchestrate them with state and branches.

Framework Selection

Match the tool to your team's real need: how much control do you need vs. how fast do you need to ship?

Flexibility vs Complexity

More flexibility usually means more code and more ways to get it wrong. Take only as much power as the problem needs.

Production Considerations

Observability, error handling, cost per run, and onboarding a new engineer matter more than which framework is "best".

When Not to Use a Framework

If one well-crafted prompt and a for-loop solve it, that's not a failure — that's the right call.

🎯 Hands-on: Framework Fit Check (15 min)

For each scenario, decide: LangGraph, CrewAI, AutoGen, or no framework — and justify it in one sentence.

  • A. A single-step FAQ chatbot with no memory needed.
  • B. A research assistant that loops, retries searches, and pauses for human approval before publishing.
  • C. A quick internal prototype where 3 role-based agents brainstorm marketing ideas together.

🤔 Curiosity spark: what's one workflow at your company that everyone assumes "needs AI agents" — but might just need a good old-fashioned script?

🎓 Key Takeaways

  • Graphs beat chains once your workflow needs branches, retries, or memory.
  • Multiple focused agents can beat one overloaded agent — but only when the task is genuinely separable.
  • Autonomy without oversight is a liability; build approval gates and monitoring in from day one.
  • The best framework is the smallest one that solves your actual problem — sometimes that's no framework at all.
